## 1. 功能概述

### 1.1 场景描述

系统管理员专属的全公司维度预警汇总面板，聚合所有项目的活跃预警，便于快速定位风险项目并督促责任人消除。

### 1.2 用户故事

> 作为**系统管理员**，我希望在项目追踪表页面打开一个抽屉，一次性查看**所有项目**的预警状态，并通过搜索、筛选快速定位目标项目；对于已确认无需处理的预警，我希望能**手动永久忽略**，避免重复出现干扰判断。

### 1.3 约束边界

- **权限**：仅 `system_admin` 角色可见，非快照查看模式
- **入口**：仅项目追踪表页工具栏
- **数据范围**：当前系统年份 + 当前报告月（可通过 query 参数切换）
- **计算方式**：每次打开抽屉时实时计算，不缓存

## 2. 预警类型定义

与项目详情 Drawer 预警区一致，共六类：

| 预警类型 | 标识符 | 标签颜色 | 触发条件 |
|---|---|---|---|
| 累计开票超总合同额 | `invoice_exceeds_contract` | 红色（danger） | AC > P（累计开票 > 总合同额） |
| 累计回款超总合同额 | `payment_exceeds_contract` | 红色（danger） | AF > P（累计回款 > 总合同额） |
| 累计回款超累计开票 | `payment_exceeds_invoice` | 红色（danger） | AF > AC（累计回款 > 累计开票） |
| 存量合同额为负 | `contract_stock_negative` | 红色（danger） | S 列（合同额 − 完成额）< 0 |
| 有完成额无工时 | `completion_no_hours` | 橙色（warning） | 当月有完成额但工时 < 0.05h |
| 有工时无完成额 | `hours_no_completion` | 橙色（warning） | 当月有工时但完成额 < 0.005 万 |

阈值规则：金额 < 0.005 视为 0；工时 < 0.05h 视为无工时。

## 3. 入口与交互

### 3.1 工具栏按钮

- **位置**：项目追踪表页工具栏，"刷新数据"按钮左侧
- **图标**：铃铛（`el-icon-bell`）
- **文案**：「项目预警」
- **可见性**：`canShowAlertsButton = isSystemAdmin && !isViewingSnapshot`

### 3.2 抽屉行为

- 点击按钮 → 抽屉从右侧滑出（800px 宽），同时触发后端计算
- 关闭抽屉 → 清空本地数据
- 每次打开均重新计算

### 3.3 卡片交互

| 卡片状态 | 点击行为 |
|---|---|
| 活跃（active） | 关闭预警抽屉 → 打开对应项目详情 Drawer |
| 已忽略（dismissed） | 无响应（卡片本体）；footer「撤回」可撤销忽略 |

**同项目多预警：** 预警按「项目号 + 预警类型」各存一条；同一项目命中多类时抽屉中出现**多张卡片**。忽略按钮仅作用于当前卡片对应的 `(project_no, alert_type)`，不会一并忽略该项目的其他类型。

演示数据：`B24264-0039`（金山中心 · 宋建生 · H-14001过滤器压差表改为远程仪表）同时命中「累计开票超总合同额」「存量合同额为负」「有完成额无工时」。

## 4. 抽屉 UI 设计

### 4.1 头部

- 标题：「项目预警总览」
- 统计摘要：「共 N 条预警（活跃 M 条），涉及 K 个项目」

### 4.2 卡片信息

每条预警以卡片形式展示：

| 信息项 | 说明 |
|---|---|
| 预警类型标签 | 彩色标签（红/橙）+ 图标 |
| 板块代码与名称 | 卡片右上角 |
| 项目编号 | 加粗显示 |
| 项目名称 | 项目号右侧 |
| 预警详情 | 具体数值描述（如「R列(存量开票额) = -12.34万」） |
| 操作区 | 卡片底部右侧（见 §4.4）；不展示首次检测时间 |

### 4.3 筛选与搜索

| 功能 | 控件 | 说明 |
|---|---|---|
| 关键词搜索 | 输入框 | 模糊匹配项目号、名称、预警类型、详情 |
| 预警类型 | 下拉多选 | 按四类预警过滤 |
| 项目板块 | 下拉单选 | 自动从当前数据中提取板块列表（去重） |
| 状态 | 下拉单选 | 全部（默认）/ 活跃 / 已忽略 |
| 重置 | 按钮 | 清空全部筛选，恢复默认状态（全部） |

### 4.4 操作区

| 状态 | 显示内容 |
|---|---|
| active | 「忽略」按钮 |
| dismissed | 「已忽略」+「撤回」按钮 |

### 4.5 统计栏

显示当前活跃预警按类型统计的计数，便于快速了解风险分布：

```
⚠ 存量开票额为负: 1   ⚠ 存量合同额为负: 1   ⏰ 有完成额无工时: 1   ⏰ 有工时无完成额: 1
```

### 4.6 分页

- 默认每页 20 条，可切换 10 / 20 / 50 / 100
- 显示当前页码与筛选后总数
- 仅在总数超过 pageSize 时显示分页控件

### 4.7 空状态

- 无预警记录：图标 + 「暂无预警记录」
- 无匹配结果：图标 + 「无匹配结果，请调整筛选条件」

## 5. 预警状态管理

### 5.1 两种状态

| 状态 | 标识符 | 含义 | 触发方式 |
|---|---|---|---|
| 活跃 | `active` | 预警条件当前满足 | 系统自动计算 |
| 已忽略 | `dismissed` | 管理员手动忽略 | 管理员手动操作 |

> 不再使用「已消除 / resolved」。条件不满足时直接删除记录。

### 5.2 状态流转

```
 (条件出现)──► active ──(条件消失)──► 删除记录
                 │
            (手动忽略)
                 ▼
              dismissed ──(撤回)──► 条件仍在则 active；否则删除
```

### 5.3 持久化规则

- 仅持久化 `active` 与 `dismissed`
- UNIQUE 约束：`(project_no, alert_type, year, month_idx)`
- 每次打开抽屉时系统重新计算：
  - 新出现 → 写入 `active`
  - 已存在活跃 → 更新 `lastSeenAt`
  - 不再出现的活跃 → **删除**
  - 历史 `resolved` 行一并清理
- 条件再次出现时作为新活跃写入（`firstDetectedAt` 为当前时间）

## 6. 手动忽略与撤回

### 6.1 操作入口

每张活跃预警卡片右下角的「忽略」按钮（`el-button size=mini type=info plain`）。

### 6.2 确认对话框

点击「忽略」后弹出确认对话框：

- **标题**：忽略预警
- **内容**：说明忽略后不再出现在活跃列表（跨月生效），并可在「已忽略」筛选中撤回
- **确认按钮**：确认忽略
- **取消按钮**：取消

### 6.3 忽略行为

- 确认后调用 `POST /api/admin/alerts/:id/dismiss`
- 后端将 `(project_no, alert_type)` 写入独立的 `project_alert_dismissals` 表
- 当前月份的预警行状态更新为 `dismissed`
- 后续月份的计算中，已忽略的 `(project_no, alert_type)` 组合不会出现在活跃列表中
- **跨月生效**：即使切换到其他月份，已忽略的预警也不会出现在活跃列表

### 6.4 撤回忽略

- **入口**：状态筛选切到「已忽略」→ 卡片 footer「撤回」按钮
- **确认**：提示若条件仍满足将重新进入活跃列表
- **API**：`POST /api/admin/alerts/:id/undismiss`
- **行为**：删除 `project_alert_dismissals` 对应行 → 将当前行暂标 `active` → 重跑 `collectAllAlerts`（条件仍在则保持活跃，已不满足则删除）
- **审计**：写入 `alert_undismiss`

### 6.5 幂等性

重复忽略同一预警不会报错（`INSERT OR IGNORE` 策略）。重复撤回已无 dismissals 记录时仍可完成状态重算。

## 7. 后端技术方案

### 7.1 数据表

#### project_alerts（预警记录表）

```sql
CREATE TABLE project_alerts (
    id                INTEGER PRIMARY KEY AUTOINCREMENT,
    project_no        TEXT NOT NULL,
    project_name      TEXT NOT NULL DEFAULT '',
    sector_code       TEXT NOT NULL DEFAULT '',
    sector_name       TEXT NOT NULL DEFAULT '',
    alert_type        TEXT NOT NULL,
    alert_label       TEXT NOT NULL DEFAULT '',
    detail            TEXT NOT NULL DEFAULT '',
    year              INTEGER NOT NULL,
    month_idx         INTEGER NOT NULL,
    status            TEXT NOT NULL DEFAULT 'active',  -- active | dismissed
    first_detected_at TEXT NOT NULL DEFAULT '',
    resolved_at       TEXT NOT NULL DEFAULT '',       -- 兼容旧列，不再写入有效值
    last_seen_at      TEXT NOT NULL DEFAULT '',
    UNIQUE(project_no, alert_type, year, month_idx)
);
```

#### project_alert_dismissals（永久忽略记录表）

```sql
CREATE TABLE project_alert_dismissals (
    project_no   TEXT NOT NULL,
    alert_type   TEXT NOT NULL,
    dismissed_at TEXT NOT NULL,
    dismissed_by TEXT NOT NULL DEFAULT '',
    PRIMARY KEY (project_no, alert_type)
);
```

### 7.2 聚合算法（`collectAllAlerts`）

1. 从 DB 加载全部项目，通过 `FormulaEngine` 计算派生字段
2. 调用 `StockValidation` 检查 R/S 列预警
3. 批量查询当年全部工时记录，按项目构建 `timesheetStats`
4. 调用 `ProjectAlerts` 检查完成额 vs 工时预警
5. **加载 `project_alert_dismissals` 表，过滤已忽略的预警**
6. 与 DB 同步（事务）：新→active / 已有→更新 / 不再→**删除**；清理历史 resolved
7. 返回 `active`+`dismissed` 列表与统计摘要（含 `dismissedCount`，无 `resolvedCount`）

### 7.3 板块名称解析

`sectorCode` 取自 `project.unit_code`（如 `S520`），通过内置 `SECTOR_NAMES` 字典映射板块中文名（与 `sector-workflow.js` 一致）。

## 9. API 端点

### 9.1 查询预警

```
GET /api/admin/alerts?year=2026&monthIdx=4
```

**参数**：`year`（可选，默认系统年份）、`monthIdx`（可选，默认当前报告月）

**响应**：

```json
{
  "alerts": [
    {
      "id": 1,
      "projectNo": "B24264-0038",
      "projectName": "...",
      "sectorCode": "S520",
      "sectorName": "金山中心",
      "alertType": "contract_stock_negative",
      "alertLabel": "存量合同额为负",
      "detail": "S列(存量合同额) = -5.00万",
      "status": "active",
      "firstDetectedAt": "2026-05-28T02:14:15.341Z",
      "lastSeenAt": "..."
    }
  ],
  "summary": {
    "total": 4,
    "activeCount": 3,
    "dismissedCount": 1,
    "byType": { "contract_stock_negative": 1, "invoice_exceeds_contract": 1, "hours_no_completion": 1 },
    "projectCount": 4
  },
  "computedAt": "2026-05-29T01:04:05.796Z"
}
```

### 9.2 忽略预警

```
POST /api/admin/alerts/:id/dismiss
Content-Type: application/json

{ "dismissedBy": "system_admin" }
```

**响应**：

```json
{
  "ok": true,
  "dismissal": {
    "projectNo": "B24264-0038",
    "alertType": "contract_stock_negative",
    "dismissedAt": "2026-05-29T01:04:05.796Z",
    "dismissedBy": "system_admin"
  }
}
```

操作同时写入审计日志（`alert_dismiss`）。

### 9.3 撤回忽略

```
POST /api/admin/alerts/:id/undismiss
Content-Type: application/json

{ "undoneBy": "system_admin" }
```

**响应**：

```json
{
  "ok": true,
  "undismissal": {
    "projectNo": "B24264-0038",
    "alertType": "contract_stock_negative",
    "year": 2026,
    "monthIdx": 7,
    "removed": true
  }
}
```

服务端删除 dismissals 后重跑当月 `collectAllAlerts`，并写入审计日志（`alert_undismiss`）。

## 10. 边界条件

| 场景 | 行为 |
|---|---|
| 空表首次打开 | 自动计算并写入全部活跃预警 |
| 重复打开 | 不产生重复记录（UNIQUE + ON CONFLICT） |
| 已忽略预警条件重新出现 | 不会出现在活跃列表（dismissals 表过滤） |
| 活跃预警条件消失 | 直接删除记录（不写 resolved） |
| 重复忽略同一预警 | 不报错（幂等） |
| 撤回忽略且条件仍满足 | 回到活跃列表 |
| 撤回忽略且条件已不满足 | 删除该预警记录 |
| 对非 dismissed 状态撤回 | 返回错误 |
| 项目号不存在 | 预警仍保留历史记录 |

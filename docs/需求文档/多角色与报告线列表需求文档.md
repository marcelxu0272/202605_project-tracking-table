# 多角色与报告线列表需求文档

> **版本：** v1.2  
> **日期：** 2026-06-05  
> **状态：** 草案讨论

---

## 1. 背景与问题

### 1.1 现状

当前原型通过「角色切换」界面模拟不同角色的视图差异，正式环境中：

- 用户无角色切换入口，但一个人可能同时拥有多个角色
- 审批流只支持单条线展示，群主管理多个板块时无法并行查看
- 所有项目在一张 Luckysheet 大表中展示，缺乏按板块/周期的组织维度

### 1.2 典型多角色场景

| 场景 | 角色组合 | 矛盾点 |
|---|---|---|
| 板块管理员兼项目经理 | sector_admin + project_manager | 是否需要以 PM 身份"提交"自己的项目？ |
| 群主兼项目经理 | group_leader + project_manager | 同一界面既要填报又要审批其他板块 |
| 板块管理员管多板块 | sector_admin × N | 需要同时看到多个板块的审批状态 |
| 板块领导兼板块管理员 | sector_director + sector_admin | 自审自批的流程跳过问题 |

## 2. 核心设计原则

### 2.1 权限向上合并

一个用户拥有多个角色时，取**权限并集**，高权限覆盖低权限：

```
system_admin > group_leader > sector_director > sector_admin > project_manager
```

**规则：**
- 板块管理员 ∪ 项目经理 → 对自己的项目拥有板块管理员级别的编辑权限，无需以 PM 身份单独"提交"
- 群主 ∪ 项目经理 → 对自己的项目直接拥有填报+提交权限，对所辖板块项目拥有审批权限
- 审批流中，当提交人本身是审批链上的某个节点时，该节点**自动跳过**

#### 2.2 功能调整策略：最小变更原则

在当前系统基础上进行**最小变更**，不新增功能页面，仅调整现有功能的定位：

**调整前（当前系统）：**
- 项目追踪表（`/editor`）：PM 和板块管理员填报编辑
- 审批流程（`/approval`）：总监和群主审批
- 审计日志、表头配置、管理设置：系统管理员专属

**调整后：**
- 项目追踪表（`/editor`）→ **只读查看**（全量数据浏览、导出）
- **填报管理（`/report-lines`）**→ **新增**，取代原审批流程页，整合填报+提交+审批
- 审计日志、表头配置、管理设置：保持不变

以下表格列出典型角色组合下，用户在**填报管理**中的数据范围和操作权限：

| 角色组合 | 填报管理中的数据范围 | 可执行操作 |
|---|---|---|
| **项目经理**（单一角色） | 仅自己项目所属板块的报告线，含历史归档 | 填报自己项目、保存草稿、提交 |
| **板块管理员**（单板块） | 所辖板块全部报告线 | 查看所有PM填报进度、催办、提交审批 |
| **板块管理员** + **项目经理** | 所辖板块全部报告线（含自己项目） | 自己项目无需PM提交环节，可直接编辑并提交审批 |
| **板块领导**（单板块） | 所辖板块全部报告线 | 查看汇总、审批、退回 |
| **板块领导** + **项目经理** | 所辖板块全部报告线 | 自己项目可直接编辑并提交，跳过板块管理员审批节点；同时可审批 |
| **群主**（管辖多板块） | 所辖多个板块的全部报告线，并行展示 | 查看多板块汇总、终审、退回 |
| **群主** + **项目经理** | 多板块报告线 + 自己项目报告线 | 自己项目跳过群主审批节点；可审批其他板块 |
| **系统管理员** | 全公司所有板块的全部报告线 | 全局查看、归档 |

**关键设计要点：**
- **填报管理统一入口：** 填报、提交、审批都在同一个功能中完成，通过列表→详情的方式组织
- **项目追踪表保留但变为只读：** 提供全量数据的浏览、筛选和导出能力，不再承担编辑职责
- **数据范围取并集：** 多角色用户看到的报告线是所有角色可见范围的并集
- **审批跳过：** 当一个用户同时是提交者和审批者时，对应审批节点自动跳过，避免自审自批

### 2.3 Git-like 数据流模型

将数据的流转类比为 Git 版本管理：

| Git 概念 | 系统对应 | 说明 |
|---|---|---|
| main 分支 | J 版（归档版） | 上一周期最终确认的权威数据 |
| fork/branch | 开启新填报周期 | 各板块从 J 版中 fork 出本板块的数据副本 |
| working copy | PM 工作区 | PM 在自己的项目范围内编辑 |
| commit + push | PM 提交 | PM 将变更提交到板块报告线 |
| code review | 板块管理员审批 | 审查变更，可退回（reject）或通过（approve） |
| merge upstream | 逐级汇总 | 板块→群组→全公司，层层合并 |
| tag/release | 新 J 版归档 | 最终确认后生成新的 J 版快照 |

**核心优势：**
- 每一层只关心"收到了哪些变更，是否接受"
- 退回 = reject，重新填报 = 修改后再次提交
- 数据隔离天然——每个板块、每个 PM 只操作自己 fork 出来的数据
- 冲突处理明确——如果同一字段被多人修改，逐级审批时由审批人决定

## 3. 报告线列表设计

### 3.1 概念定义

**报告线（Report Line）**：以「板块 × 月度周期」为单位的工作项，是填报、审批、归档的最小管理粒度。

每条报告线包含：
- 所属板块
- 所属周期（年月）
- 当前状态（开放填报 / 审批中(板块领导) / 审批中(群主) / 已退回 / 已完成 / 已关闭）
- 包含的项目数量
- 当前审批节点
- 最后更新时间

### 3.2 列表视图（填报管理首页）

所有角色进入系统后，首先看到的是**报告线列表**，根据角色不同，可见范围不同：

| 角色 | 可见报告线 | 列表展示重点 |
|---|---|---|
| 项目经理 | 自己项目所属板块的报告线（含历史归档） | 我的填报状态、是否需要操作 |
| 板块管理员 | 所辖板块的所有报告线 | 板块整体进度、待审批数 |
| 板块领导 | 所辖板块的所有报告线 | 待我审批的报告线 |
| 群主 | 所辖多个板块的所有报告线 | 多板块并行状态一览 |
| 系统管理员 | 全部报告线 | 全局进度监控 |

### 3.3 列表信息结构

| 板块 | 周期 | 状态 | 操作 |
|---|---|---|---|
| 板块A | 2026年6月 | 🟡 开放填报 | 填报 · 导出 |
| 板块B | 2026年6月 | 🔵 审批中(板块领导) | 审批 · 查看 · 导出 |
| 板块A | 2026年5月 | ✅ 已完成 | 查看 · 导出 |
| 板块B | 2026年5月 | ⛔ 已关闭 | 查看 · 导出 |

**操作列可见性规则（角色 × 状态）：**

| 角色 | 开放填报 | 已提交(PM) | 审批中(板块领导) | 审批中(群主) | 已退回 | 已完成 | 已关闭 |
|---|---|---|---|---|---|---|---|
| 项目经理 | 填报 | 查看 | — | — | — | — | 查看 |
| 板块管理员 | 填报 · 导出 | — | 查看 · 导出 | 查看 · 导出 | 填报 · 导出 | 查看 · 导出 | 查看 · 导出 |
| 板块领导 | 查看 | — | 审批 · 查看 · 导出 | 查看 · 导出 | 填报 · 导出 | 查看 · 导出 | 查看 · 导出 |
| 群主 | 查看 | — | 查看 · 导出 | 审批 · 查看 · 导出 | 填报 · 导出 | 查看 · 导出 | 查看 · 导出 |
| 系统管理员 | 查看 · 导出 | — | 查看 · 导出 | 查看 · 导出 | 查看 · 导出 | 查看 · 导出 | 查看 · 导出 |

**操作说明：**
- **填报：** 点击进入详情页编辑数据（仅开放填报/已退回状态下可用）
- **审批：** 点击进入详情页查看 diff 并执行通过/退回（仅当前审批节点对应角色可见）
- **查看：** 点击进入详情页只读浏览数据
- **导出：** 将当前报告线数据导出为 Excel

### 3.4 列表筛选与排序

- **状态筛选：** 全部 / 需要我操作 / 进行中 / 已完成 / 已关闭
- **板块筛选：** 按板块名称（多板块用户适用）
- **周期筛选：** 按年月
- **默认排序：** 需要操作的在前 → 进行中 → 已完成 / 已关闭（按时间倒序）

### 3.5 状态机与视角模型

#### 3.5.1 报告线客观状态机

报告线采用统一客观状态机，状态本身不按角色拆分，但不同角色在列表中看到同一状态时，显示差异化的操作提示：

```
报告线客观状态流转：

开放填报 → 审批中(板块领导) → 审批中(群主) → 已完成
    ↑              │                  │
    └── 已退回 ←──┴──────────────────┘
    
超期未完成 → 已关闭
```

| 状态 | 说明 | 触发条件 |
|---|---|---|
| **开放填报** | 板块管理员和 PM 可编辑的阶段 | 系统管理员手动发起填报时创建 |
| **审批中(板块领导)** | 板块领导审批阶段 | 板块管理员提交审批 |
| **审批中(群主)** | 群主终审阶段 | 板块领导审批通过 |
| **已退回** | 被退回至板块管理员，需重新编辑 | 板块领导或群主退回 |
| **已完成** | 当前报告线流程走完，数据合并至总表 | 群主审批通过 |
| **已关闭** | 当月填报期内未走完审批流程 | 超期未完成 |

**关键规则：**
- 报告线从「开放填报」到「审批中」的触发是**板块管理员提交审批**，而非 PM 提交
- PM 提交仅表示 PM 将自己的数据提交给板块管理员，不改变报告线的客观状态
- 「已退回」后回到「开放填报」，板块管理员和 PM 可重新编辑
- 「已完成」表示单个报告线走完流程，数据合并到总表，不等于 J 版归档
- 「已关闭」为终态，不可重新打开

#### 3.5.2 PM 视角状态

PM 有独立的三状态视角，与报告线客观状态解耦：

```
PM 视角状态流转：

开放填报 → 已提交（等待板块管理员处理）
         → 已关闭（板块管理员已提交审批，PM未提交则自动关闭）
```

| PM 视角状态 | 说明 | 对应的报告线客观状态 |
|---|---|---|
| **开放填报** | PM 可以编辑自己的项目 | 开放填报 |
| **已提交** | PM 已将数据提交给板块管理员 | 开放填报 / 审批中(板块领导) / 审批中(群主) |
| **已关闭** | PM 填报入口已关闭，无法再编辑 | 审批中(板块领导) / 审批中(群主) / 已关闭 |

**「已关闭」触发条件：**
- 当板块管理员提交审批时，所有未提交的 PM 状态自动变为「已关闭」
- PM 在「已关闭」状态下只能查看自己的项目数据（只读），无法编辑

> **注意：** 「已提交」只是 PM 的视角状态，不是报告线的客观状态。PM 提交后，报告线仍处于「开放填报」，直到板块管理员提交审批才进入「审批中」。

## 4. 报告线详情（点入后）

### 4.1 进入逻辑

点击列表中的报告线进入详情页，详情页内容根据用户角色和报告线状态动态展示：

| 用户角色 | 报告线状态 | 详情页行为 |
|---|---|---|
| 项目经理 | 开放填报 | 只显示自己负责的项目，可编辑 |
| 项目经理 | 审批中(板块领导) / 审批中(群主) | 只显示自己的项目，只读 |
| 项目经理 | 已退回 | 只显示自己的项目，可重新编辑 |
| 项目经理 | 已关闭 | 只显示自己的项目，只读（填报入口已关闭） |
| 板块管理员 | 开放填报 | 显示板块所有项目，可催办/查看进度 |
| 板块管理员 | 审批中(板块领导) | 显示板块所有项目 + 变更 diff，等待板块领导审批 |
| 板块领导 | 审批中(板块领导) | 显示板块汇总 + 变更 diff，可批准/退回 |
| 群主 | 审批中(群主) | 显示板块汇总 + 变更 diff，可批准/退回 |

### 4.2 详情页结构

```
┌──────────────────────────────────────────────────────────────────┐
│  ← 返回列表    板块A · 2026年6月                               │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  [状态条] 开放填报 → 审批中(板块领导) → 审批中(群主) → 已完成      │
│           ^^^^                                                   │
│                                                                  │
│  ┌─ 操作区 ───────────────────────────────────────────────────┐  │
│  │  [保存]  [提交]  [导入]  [导出]  ...                       │  │
│  │  （与当前项目追踪表的功能区保持一致）                      │  │
│  └────────────────────────────────────────────────────────────┘  │
│                                                                  │
│  ┌─ 项目数据表 ──────────────────────────────────────────────┐  │
│  │  (Luckysheet / 表格组件)                                   │  │
│  │  PM: 只显示自己的项目行                                    │  │
│  │  板块管理员+: 显示板块全部项目                             │  │
│  └────────────────────────────────────────────────────────────┘  │
│                                                                  │
│  ┌─ 审批记录 ────────────────────────────────────────────────┐  │
│  │  时间轴: 提交 → 初审通过 → ...                            │  │
│  └────────────────────────────────────────────────────────────┘  │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 4.3 PM 视角的特殊说明

- PM 点入报告线后，**只能看到和编辑自己负责的项目**（与原先 Luckysheet 中的行级权限逻辑一致）
- 历史已完成的报告线也出现在列表中，PM 可点入查看自己项目的历史数据（只读）
- 如果 PM 只有一条当前需要操作的报告线，列表仍正常显示（因历史记录也在列表中）

## 5. Git-like 数据流详细设计

### 5.1 周期开启（手动发起填报 / Fork）

系统管理员在填报管理页点击「手动发起填报」，弹窗展示以下内容供核对后确认发起：

1. **周期信息（只读）**：报告月（取管理设置中 `reportingMonth`）、Baseline J 版版本号（取 `latestJVersion`）
2. **审批人员核对表**：逐板块展示板块管理员、板块审批、项目群审批的配置人员，以及项目数与是否已存在；人员来源标签分为「已配置」「平台默认」「未配置」
3. **无 J 版时**：弹窗提示先完成归档，发起按钮禁用；全部板块已存在报告线时同样禁用

```
系统管理员 点击「手动发起填报」→ 弹窗预览（GET /api/report-lines/fork-preview）
    │
    ├── 核对：报告月、J 版 baseline、各板块审批链路人员
    │
    └── 确认发起（POST /api/report-lines/fork-period）
            │
            ├── 板块A 报告线创建 ← fork(latestJVersion, 板块A的项目集)
            ├── 板块B 报告线创建 ← fork(latestJVersion, 板块B的项目集)
            ├── 板块C 报告线创建 ← fork(latestJVersion, 板块C的项目集)
            └── ...（十二板块；已存在则跳过）
```

**Fork 的数据内容：**
- 从最新 J 版快照（`latestJVersion`）中提取该板块所属的项目数据（确保 baseline 一致）
- 作为本周期的 baseline（基线）
- PM 的编辑基于此 baseline 进行
- 已存在同周期同板块报告线的将**跳过**，不会覆盖

### 5.2 填报与提交（Commit & Push）

```
PM 编辑自己的项目数据（working copy）
    │
    ├── 保存草稿 = local commit（不影响他人）
    │
    └── 提交 = push to 板块报告线
         │
         └── 系统记录: 哪些字段相对 baseline 发生了变更（diff）
```

### 5.3 审批与合并（Review & Merge）

```
板块管理员 编辑/汇总板块项目数据（PM 可填报但非必须）
    │
    ├── 查看 diff（相对 baseline 的变更汇总）
    │
    └── 提交审批 → 板块领导
         │
         板块领导审批
         │
         ├── 退回 → 退回到板块管理员
         │
         └── 通过 → 提交给群主
              │
              群主终审
              │
              ├── 退回 → 退回到板块管理员
              │
              └── 通过 → 标记为待归档
```

### 5.4 归档（Merge to Main / Tag）

```
系统管理员 确认归档
    │
    ├── 所有板块报告线汇总 → 生成新 J 版快照
    ├── 新 J 版成为下一周期的 main 分支
    └── 所有报告线状态更新为「已完成」
```

### 5.5 变更追踪（Diff）

每一级审批时，系统展示的 diff 内容：

| 审批层级 | Diff 基线 | Diff 内容 |
|---|---|---|
| 板块管理员 | fork 时的 baseline | 各 PM 修改了哪些字段 |
| 板块领导 | 同上 | 板块管理员确认后的汇总变更 |
| 群主 | 同上 | 板块领导确认后的最终变更 |

## 6. 导航与路由设计

### 6.1 侧栏导航（按角色动态显示）


### 7.2 多角色合并规则

```javascript
// 伪代码：计算用户有效权限
function resolvePermissions(user) {
  const roles = user.roles; // e.g. ['sector_admin', 'project_manager']
  
  // 取所有角色权限的并集
  const permissions = roles.reduce((acc, role) => {
    return union(acc, ROLE_PERMISSIONS[role]);
  }, {});
  
  // 数据范围取并集
  const dataScope = {
    sectors: union(...roles.map(r => getSectorScope(user, r))),
    projects: union(...roles.map(r => getProjectScope(user, r))),
  };
  
  return { permissions, dataScope };
}
```

### 7.3 审批流自动跳过

当用户同时拥有提交者和审批者角色时，审批节点自动跳过：

| 场景 | 行为 |
|---|---|
| 板块管理员提交自己的项目 | 板块管理员直接提交审批，跳过 PM 提交环节 |
| 板块总监兼板块管理员 | 跳过板块总监审批节点，直接进入群主审批 |
| 群主兼板块管理员 | 跳过群主审批节点，仅需板块总监审批（若也兼任则直接归档） |
